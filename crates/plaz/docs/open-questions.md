# plaz — open questions

State on 2026-11-14. The design is in [design.md](design.md). Rust and Python functions (a preview) get decision flowcharts, a coverage line and call targets in four forms; C/C++, JS/TS (including Vue and Svelte scripts), Go and shell get a "not covered yet" note.

## Agents

## Resolution rules

- **Rule in force** (owner decision, 2026-11-14): a call target is certain by default and uncertain only on a visible contradiction in the file. More certain links at the price of rare wrong ones is accepted; workarounds come later.
- **`self` / `Self` calls** are "resolved" only when no subclass in the project overrides the method; otherwise "one of: own or overrides" (a text-based rule: a project class whose signature names this class and defines the same method).
- **When a path is "known external".** The rule so far: a std root, or an import that resolves to no project file. Everything else unknown is "hidden".
- **Receiver types from struct fields** (`self.items.get()`) are not read, so such calls show as "one of". Accept as a known gap or read field types.
- **SCIP indexes.** When a repo already has one, it could collapse "one of" into single links. Deferred.

## Known limitations of call targets (accepted, workarounds later)

- **A path root that is an outside crate named like a project file** is taken for the file: in `src/a.rs`, `c.get()` on `c: config::Config` and `config::load()` link to `src/config.rs` though nothing says `use crate::config`. The same holds for `use b::helper;` with a project `b.rs` the file does not declare.
- **Inline modules are not scopes.** `mod m { pub fn both() {} pub fn f() { both(); } }` beside a file-level `both` reads "one of" both. A name only the file level has links from inside `m` though it would need `super::`. `m::inner()` reads "target not visible".
- **Two crates in one tree.** `crate::solo::only()` in crate `a` links to `b/src/solo.rs` when only crate `b` has a `solo.rs`.
- **A comment inside a `use` list hides the names after it.** `use other::{ x, // note` then `helper,` on the next line: `helper()` links to the file's own `helper` instead of "one of: helper, or outside".
- **`#[path]` and same-named functions under different modules** are told apart only by count: two `run` read "one of", one reads certain.
- **A re-export under another name** (`pub use crate::b::Store as Value;` reached through a glob): `v.get()` on `v: Value` reads "one of: Store::get, or outside the project" only because the method name is unique.
- **Type aliases.** After `type Alias = S;`, `a.own()` on `a: Alias` and `Alias::mk()` read "target not visible".
- **A crate name the tree has no `Cargo.toml` for** (`mycrate::run()` in `main.rs`) reads "target not visible"; the imported form (`use mycrate::run; run()`) reads "one of: run, or outside the project".
- **A path through a re-export from another crate** (`pub use other::helper;` in crate `app`, then `app::helper()`) reads "one of: helper, or outside the project": the path links only into the crate it names, and `helper` is defined elsewhere.
- **A leading `::`** (`::utils::load()`) reads "target not visible".
- **A function or inline module named like an own crate** counts as a local module of that name: with `fn utils() {}` in the file, `utils::load()` links to the project file `utils.rs` instead of the crate `utils`.
- **An own crate named `core`, `std` or `alloc`** loses to the standard library: `core::run()` reads "outside the project".
- **A `Cargo.toml` in a fixture directory** (one the walk reaches, such as `examples/fixture/Cargo.toml`) makes its package name a project crate.
- **Names generated by macros** are invisible; a call to one reads "outside the project" when nothing else has the name.
- **A delegating wrapper lists itself under "may call".** In `fn get(&self, k) { self.map.get(k) }` the call `self.map.get(k)` keeps `get` itself as a candidate, so `get` appears in its own "Called from" as "may call".
- **Both imports of one name aliased.** With the project import and the outside import of a name both aliased, a call of it reads "outside the project".
- **`crate::b::S::new()` with two project types `S`** reads "one of".
- **`Square::default()` through `impl Default`** reads "target not visible".
- **A file the parser rejects entirely** gets no page; it is named with the unreadable files (`warning: could not read <path>`).
- **Python: a constructor call as the receiver.** `Cls().run()` reads "one of: Cls::run, or outside the project".
- **Python: a typed receiver does not walk the bases.** With `class Child(Base)` and `Base.inherited`, `c.inherited()` on `c: Child` reads "one of: Base::inherited, or outside the project"; `self.inherited()` inside `Child` is certain.
- **Python: `self.f()` that neither the class, a project base nor a project subclass defines** reads "one of: <every project method `f`>, or outside the project": `self.callback()` on an attribute set in `__init__`.
- **Python: `super().f()` follows the bases as written,** not the method order of the object's class: in `class C(A, B)` it links to `A.f` even when a subclass's order puts another class between. In a class without bases (a mixin) it reads "one of …, or outside the project".
- **Python: classes are told apart by name.** A subclass counts for every project class of the base's name; two classes `Base` in different files share their subclasses.
- **Python: imports inside a class body** are read as module-level imports: `class A:` with `import json` in its body.
- **Python: an import inside a function body** makes its names "target not visible": `def f(): from .c import go; go()`. A name from a project `from m import *` reads "one of …, or outside the project".
- **Python: which directory is on the import path is not known.** An absolute import is the project's when its root is a directory whose parent is no package (has no `__init__.py`), or a module in no package, at the top of the tree or in a directory the importing file is under. In a package the standard library wins: `import json` in `app/x.py` beside `app/json.py` and `app/__init__.py` is outside the project. In a tree without `__init__.py` the sibling is taken as the project's: the same import links to `app/json.py`. A module of that name in an unrelated directory outside any package (`import logging` in `pkg/a.py` with `app/logging.py`) reads "one of …, or outside the project", as does `import mod` with `pkg/mod.py` and `top/mod.py` in no package. A project import whose module is no file of the tree (`from app.missing import load`) reads "target not visible".
- **Python: a name re-exported by assignment** is not followed: with `run = core.run` in `pkg/__init__.py`, `pkg.run()` reads "target not visible". `from .core import run` and `from .core import *` are followed.
- **Python: one alias bound twice at file level** keeps its first binding: after `import a as m` and later `import b as m`, `m.f()` links to `a.f`.
- **Python: a module alias shadowed by a local still links.** In `def f(): au = 3; au.quote()`, with `from app import utils as au` at file level, `au.quote()` links to `app/utils.py`'s `quote`.
- **Python: an attribute or a call result as the receiver** reads "outside the project" when no project method has the name, even when a project module function has it: `self.au.quote()` and `make().quote()` with `quote` in `app/utils.py`.
- **Python: `import pkg.util` then a bare `g()`** reads "one of: g, or outside the project" with `pkg/util.py`'s `g`, though the import binds only `pkg` and `g` is not defined in the file.
- **Python: nested classes** are not followed: `Outer.Inner.im(i)` and `self.Inner()` read "outside the project" though both are the project's.
- **Rust: a trait and a struct of one name in one file** are one type to the resolver: with `trait Store { fn get(&self); }` and `impl Store { fn get(&self) {} }`, `self.get()` inside `impl Store` reads "one of: Store::get, Store::get, or outside the project" instead of linking to the struct's `get`.

## Known limitations of the chart (accepted)

- **A `break` hidden in a macro** is drawn as an `exit not drawn` edge from the loop to what follows it, or to `end`. It is found by a `break` token in a macro in the loop's body: `loop { tokio::select! { _ = stop.recv() => break, } }`. A macro that breaks without the token is seen only when code follows the loop directly; a `break` of a loop written inside the macro gives a spare exit.
- **A labelled hidden `break 'a` out of a nested loop** is drawn as an exit of the inner loop to the outer loop: `'a: loop { loop { select! { _ = stop.recv() => break 'a, } } }`. The outer loop gets its exit only when code follows it.
- **A hidden `return` inside a macro** is not drawn: `select! { _ = stop.recv() => return, … }`.
- **An async block with a `return`, awaited in place,** is a sub-chart beside the path, not on it: `let v = async { if c() { return 1; } 2 }.await;`.
- **Both `#[cfg(...)]` twins of a function body** are drawn one after the other: `#[cfg(unix)] loop { … }` then `#[cfg(not(unix))] loop { … }`.
- **`break 'a` out of a labelled block** has no outgoing edge: `'a: { if c { break 'a; } step(); }`.
- **A trailing comment on a one-line `if … else` or `let … else {` row** is attached to both arms: `if c { a() } else { b() } // note`.
- **Own-line comments inside a block that is not a decision** are not shown: `{ // note` above `step();` in a plain block or a loop body.
- **`Ok(…)`, `Some(…)`, `Err(…)` and each prefix of a call chain** are their own call nodes: `Ok(xs.iter().map(f).collect())` gives `xs.iter()`, `xs.iter().map(f)`, `xs.iter().map(f).collect()` and `Ok(…)`.
- **`?` and a function's tail value** are not drawn; `?` is counted on the coverage line: `let v = load()?; v`.
- **A call used as a condition** appears as a call node and again in the diamond: `if ready() { … }`.
- **A method call on a receiver whose type is not visible** (`x.iter()`, `v.len()`) reads "one of: <project methods of that name>, or outside the project" when the project has methods of that name. Typing locals and struct fields would narrow it.
- **A file tree-sitter cannot fully parse** carries the "Syntax errors" note even when it is valid for its real compiler or shell (seen with shell scripts and C++ headers using compiler built-ins).
- **Python: `try` is a decision** between the body (`try`, yes) and the handlers; the jump from inside the body to a handler is not drawn. Counted under `try`.
- **Python: an exit passing through `finally`** is not drawn: after `try: return load()` / `finally: close()` no edge leads from `return load()` to `close()`; the same holds for `break`, `continue` and an exception leaving a handler. Counted under `try`. A `finally` that no path falls into is a sub-chart `finally L<n>` beside the path.
- **Python: the `else` of a loop that never ends** (`while True: … else: …`) is a sub-chart `else, never run`.
- **Python: `assert check(v), msg(v)`**: `msg(v)` runs only when the assert fails; it is drawn in sequence after `check(v)`.
- **Python: default argument values** (`def f(x=dflt()):`) are drawn as the first steps of the function though they run once, when the `def` runs.
- **Python: module-level code is not charted.** A call or a decision outside any `def` or `class` (`data = load()`, `if __name__ == "__main__": main()`) is drawn nowhere; the page says `Module-level code is not charted.` Imports, docstrings and assignments of plain values (`LIMIT = 3`) do not count. Any other statement does, so a guarded import (`try: import json` / `except ImportError: json = None`) also gets the line. Code in a class body is not checked. The functions it calls read `Called from: none found` for it.
- **Test code is not charted.** Functions the shared code layer marks as tests (in a test file such as `tests/it.rs` or `pkg/test_thing.py`, or under `#[cfg(test)]`) get no section; the page says `Test code is not charted: 2 functions.` Calls from them are not counted under "Called from".
- **Nesting deeper than the build's 512 MB stack holds** still aborts the whole build with a stack overflow, naming no file. A 20,000-term `g() + g() + …` and 20,000 nested `if`s build (the latter in about 30 s).

## Facts wiki-code does not expose yet

- **Where a `use` is written** (file level, a body, an inline module): `CodeFile.imports` is one flat list, so a name both defined and imported in a file is never certain, and a comment inside a `use` list cannot be told from the names. Needed: imports with their enclosing item.
- **Crate names and roots.** The project's own crate names are read from the tree's `Cargo.toml` files (`[package]` and `[lib]` names), and a path rooted at one is the project's. A dependency's crate name is still unknown, so a path rooted at one reads "target not visible". Which file is a crate root, and which crate a file is in, are not known beyond the manifest's directory.
- **The module tree.** `Imports::resolve` returns nothing for `mod x; use x::f;` and picks one of two same-stem files silently; inline modules are not modules to `Index` (`is_module`, `qualified`), and `fns_here` ignores them.
- **Whether a `Type` item is a trait** (read from the signature text today).
- **Alias folding** is file-wide and silent, and is skipped when a parameter list mentions the alias (`fn f(c: Cache)` keeps `Cache::get` unfolded); the resolver only sees the result.
- **`defined`** holds public names only; "the file defines it" is read from `items`.
- **Imports per language.** `Imports::resolve` matches import segments across languages (`import json` in a Python file resolved to a Rust `json.rs`), so plaz reads Python's imports from the tree and resolves them against the Python files only. Needed: imports as module, name and alias, with their enclosing item, resolved within one language.
- **Call sites arrive with aliases replaced.** After `from m import f as g`, `g()` arrives as a call of `f`; the name as written is read back from the call's text.
- **A Python class's bases** are read from the signature text.

## Rendering

- **A trailing comment on the `else` row** (`} else // note` with the `if` on the next line) is shown nowhere.
- **Only the first comment on a decision's own row is kept.**
- **`<T as Display>` in link text** may render as an HTML tag in Quartz. Open until the renderer research.
- **Python method links read `A::step`,** not `A.step`: the name comes from the shared code layer.
- **No `# title` heading on a page.** Quartz shows the front-matter title; how Obsidian shows it is open until the renderer research.

- **Mermaid limits.** Mermaid's defaults stop at 500 edges or 50,000 characters. The design says charts are complete; the map emits such a chart whole, followed by a line pointing to the Calls list as the complete view. Needs a check in Quartz and Obsidian with the largest real functions (39 diamonds in one measured function).
- **Clicks in Obsidian.** Mermaid clicks to internal notes probably do not work there; the wikilink list is the fallback. To be checked.
- **mermaid-cli in CI.** It needs Node; the check is designed as a test run locally only. Decide whether CI gets Node.
- **Comment cap.** The design picked 6 lines shown whole, then `comment: N lines at path:a-b`. Not measured.
- **Non-ASCII function names** get the headings `fn`, `fn_2`, …: the heading is the anchor, so the name is only on the signature line, and such anchors shift when another one is added above.
- **Output grows as calls × namesakes.** The "one of" list is not capped: 20,000 untyped `x.get()` calls with 50 project methods `get` give 20,000 "may call" lines under each `get` (a 109 MB map). Measured trees stay at 19 candidates or fewer.

## Measured

First measurement gate, 2026-11-14. It is an early check that the call targets and charts are sound before more is built on them, not a release decision.

- **What was run.** A release build over five trees: this repository's sources of the time (Rust, both crates; judged), two small Python tools (two files each; a smoke check), and a C++ trading system with Rust and Python parts and a second project (both seen during development, so they do not decide the result). Each tree was built three times into an empty vault.
- **Determinism.** The three builds were byte-identical for every tree; nothing was printed to stderr.
- **Labels, every node.** 6,822 diamond labels and 27,567 call-node labels were unescaped and compared with the source text at their lines: 0 mismatched. Every Calls entry has its node. No node of live code lacks an incoming edge.
- **Call targets on this repository's sources of the time** (585 functions, all with a chart; 7,588 calls): certain 930 (12.3%), one of 286 (3.8%), outside the project 5,849 (77.1%), target not visible 523 (6.9%).
- **Read by hand** (readers given the four forms and the source, not the expected answers). this repository's sources: 100 certain, 40 one of, 30 outside, all right. The two projects seen during development: 100, 40 and 30 each, all right. The first small Python tool: all 5 certain and 30 outside right. The second: all 16 certain and 30 outside right. The one wrong answer of the first pass (a path rooted at a workspace crate's own name read "outside the project") was fixed before this record; own crate names are now read from the manifests.
- **Python is a smoke check.** The two judged Python trees have 17 functions and 238 calls together.
- **Size and time.** this repository's sources: 70 pages, 1.66 MB, 0.46 s. The second project: 154 pages, 779 functions, 2.27 MB, 0.48 s. The C++ trading system: 847 pages, 1,319 Rust and Python functions, 4.09 MB, 1.64 s; one chart there is over Mermaid's default limits, 8 pages carry the syntax-errors note, 15 loops have an `exit not drawn` edge.
- **Headroom, not defects.** Most "one of" answers are method calls on a receiver whose type is written in the function but not read (locals and struct fields). Of the 35 "target not visible" answers read in the last pass, 11 had a project target a reader could name: enum variant constructors (`Value::Int(…)`), Python class constructors, one function nested in another.
- **Not measured.** Hidden directories are not walked. C/C++, JS/TS, Go and shell have no charts yet. Rendering in Quartz and Obsidian was not checked.

## Walking the tree and writing the vault

- **What the walk reads.** `.gitignore` files and the user's global gitignore are honoured; hidden directories and `vendor`, `node_modules`, `third_party`, `superpowers` are skipped; symlinks are not followed. Skipped files are not counted on output.
- **One vault holds the map of one source tree.** Building tree B into tree A's vault removes A's pages. A build that finds no code file warns (`warning: no code file found in <source>, the map is left as it is`) and removes nothing.
- **A file at a page path that is not a map page is left alone** and counted: `map: 1 written, 0 unchanged, 0 removed, 1 left alone`. A page cut inside its front matter by a crash before this version cannot be told from a user's file; delete it by hand. Pages are now written through a temporary file and renamed, and an empty file at a page path is rewritten.
- **`--source=DIR` needs a UTF-8 `DIR`;** `--source DIR` takes any path.
